Cos'è il sistema

DIVA — Dubbing Invoice Verification Agenda

Sistema web per la gestione, emissione e archiviazione delle fatture nel mondo del doppiaggio italiano, con calcolo automatico dei contributi ENPALS. Nato come simulatore desktop, oggi è un'app mobile-first con assistente vocale integrato e un calendario appuntamenti collegato ai dati reali.

🎯 Perché esiste
I professionisti del doppiaggio (doppiatori, direttori di doppiaggio, assistenti, dialoghisti/adattatori) devono emettere fatture con calcoli complessi: tariffe ENPALS diverse per ruolo e tipo di opera, contributi previdenziali, ritenute d'acconto, anzianità contributiva (SY/SC/SA). DIVA automatizza completamente questi calcoli, guida l'utente passo passo, archivia tutto su cloud e permette la consultazione storica da qualsiasi dispositivo.
👤 Utenti target
Doppiatori — imponibile per righe e turni
Direttori di doppiaggio — tariffa fissa per turno, nessuna riga
Assistenti al doppiaggio — tariffa fissa per turno
Dialoghisti/Adattatori — tariffa per tipo opera
Amministratori — gestione completa del sistema
⚡ I due macro-moduli
1. Motore di fatturazione — completo e in produzione: wizard mobile, calcolo automatico, PDF su cloud, assistente vocale per consultazione.

2. Calendario appuntamenti — integrato e in produzione, quattro viste (Giorno/Settimana/Mese/Anno), dati reali su Supabase, genera fatture vere riusando lo stesso motore di calcolo del wizard direttamente dagli appuntamenti pianificati.

Sicurezza

Come sono protetti i dati

🔑 Chiavi API — mai nel frontend
La service key Supabase, la API key tts.ai e la API key Claude/Anthropic vivono esclusivamente nelle variabili d'ambiente di Render. Il server fa da intermediario per ogni chiamata — mai una chiave sensibile nell'HTML pubblico su GitHub.
🔐 Autenticazione
Login → token Bearer, salvato in sessionStorage, passato in ogni chiamata successiva. Dal Giugno 2026 i token sopravvivono ai riavvii di Render grazie alla tabella sessioni su Supabase (prima si perdevano ad ogni riavvio del server gratuito).
📄 PDF privati con URL firmati
Bucket Storage privato. Ogni apertura/download genera un signed URL univoco valido 1 ora. Dopo la scadenza il link non funziona più — i PDF non sono mai accessibili liberamente su internet.
👥 Isolamento per utente
Ogni chiamata alle fatture è filtrata per nominativo dell'utente loggato — un utente normale vede solo le proprie fatture, mai quelle di altri. Solo l'admin vede tutto.
🔒 Campo nominativo bloccato
Gli utenti normali non possono modificare il proprio nominativo nel wizard — previene la possibilità di compilare fatture a nome di qualcun altro.
📋 Log completo e verificabile
Ogni azione (login, CRUD, stampe, salvataggi) è loggata con utente, ruolo, dettaglio, IP. Sincronizzato automaticamente su GitHub ogni 30 secondi come backup indipendente da Supabase.
⚠ Punto debole noto — RLS non ancora attivate formalmente (ma la strada è sgombra)

Le tabelle Supabase non hanno ancora Row Level Security attivata a livello di database: l'accesso con anon key non è bloccato lì, solo a livello applicativo (dal server). Il lavoro preparatorio è però concluso: nessun file parla più direttamente con Supabase usando la chiave anon (chiuso il 3 luglio, verificato di nuovo il 5, vedi Fase 17 e 19 nello storico) — tutto passa dal server con la chiave service_role, che l'attivazione delle RLS non toccherebbe in alcun modo. L'attivazione vera e propria (comandi SQL su ogni tabella) resta da fare — vedi tab "Da fare" — ma è oggi un'operazione sicura e senza rischio di rompere nulla.

Affidabilità

Robustezza del sistema

🧵 ThreadingHTTPServer
Il server Python era single-threaded: una chiamata lunga (es. polling tts.ai di 25 secondi) bloccava tutte le altre richieste, login incluso, causando errori 502. Risolto passando a ThreadingHTTPServer con daemon_threads=True.
💾 Doppia modalità DB
Online (Supabase, default) / Locale (SQLite fallback) tramite variabile USE_SUPABASE. Garantisce continuità anche in caso di problemi con Supabase, per uso admin offline.
🔄 Sessioni persistenti
Prima di Giugno 2026, un riavvio di Render (piano gratuito, sonno dopo inattività) disconnetteva tutti gli utenti. Ora il token viene recuperato automaticamente dalla tabella sessioni su Supabase.
🛡 Filtro colonne salvataggio
Fix di Giugno 2026: _COLS_SB filtra le colonne effettivamente esistenti su Supabase prima dell'invio, evitando errori di scrittura quando lo schema locale e remoto divergono temporaneamente.
⚠ Rischi noti da monitorare

Render free tier — si addormenta dopo 15 min di inattività, cold start ~30 secondi al primo accesso; 750 ore/mese totali, 500 minuti di build al mese (esauriti una volta il 30 giugno 2026 per troppi push di test ravvicinati, sbloccati automaticamente il 1° luglio col reset mensile).

Supabase free tier — il progetto va in pausa dopo 7 giorni di inattività. Risolto il 6 luglio: ping immediato all'avvio del server (non più affidato solo a un timer interno, che non arrivava mai in fondo se il server si riaddormentava prima) + GitHub Action schedulato due volte a settimana che sveglia il server anche in caso di totale inattività — vedi Fase 20 nello storico.
